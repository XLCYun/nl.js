# 代码生成 Harness

状态：用户已于 2026-10-10 确认完整方案并要求开始实现。实施工单见[本地任务图](../../.scratch/code-generation-harness/map.md)。

## 用户提出的要求

- 在 core 引入 Harness 层，使用主循环维护多轮 messages。
- 模型一轮回复结束时，如果没有调用 `final_output`，追加一条提醒消息并继续请求模型。
- 最终生成代码仍通过 `final_output({ asyncFuncBody: string })` 提交。
- Harness 只负责 OpenAI 代码生成会话，缓存、函数体包装、eval 和 Jev 独立判断路径保持原样。
- 参数错误也反馈给模型修正，不再仅限于漏调用时提醒。
- 轮数上限可配置，默认值为 10 轮。
- 配置通过项目注入的特殊全局对象赋值，不使用新增环境变量。
- 继续只提供 `final_output` 工具，并保留强制指定该工具的 `tool_choice`。

## 当前实现与变化点

- [core/index.js](../../packages/core/index.js) 在代码缓存未命中后调用一次 Chat Completions，将响应交给 `parseFinalOutput`，再包装、缓存函数体。
- 请求强制指定 `final_output`，关闭并行工具调用。当前没有会话循环。
- 现有解析要求响应以 `tool_calls` 结束，包含且仅包含一个有效的 `final_output` 调用。正常文字回复、拒绝、截断和无效提交均报错。
- Jev 在进入代码缓存和 OpenAI 请求之前独立分流。
- 本设计调整[原提交协议](final-output-tool.md)中“缺少调用或参数错误时立即失败，不追加模型纠错请求”的决定，改为在会话上限内反馈错误并继续。拒绝、过滤、截断及损坏响应仍失败。

一次模型回复结束，不等于整个代码生成过程完成。普通文字回复不能充当生成代码；只有通过工具提交的函数体才能成为生成阶段的结果。

代码生成会话与代码提交的术语已记录在 [GLOSSARY.md](../../GLOSSARY.md)。错误提交可以再次修正，因此“最终有效提交”与“整个会话只允许一次工具调用”不再等价；原提示词也需要随之调整。

## 轮数配置

轮数使用项目注入的特殊全局对象配置，不新增 `NLJS_MAX_ROUNDS` 环境变量。

Babel 在每个含 `nl` 的文件中注入 `__NLJS_GLOBAL`，并原样作为 `generate({ global: __NLJS_GLOBAL, ... })` 的参数传入。历史提交 `b57b102` 曾从该对象读取 `openaiApiKey`、`openaiBaseURL` 和 `openaiModel`，提交 `f69773e` 移除了这些回退入口。用户所说的特殊全局配置入口有历史依据；当前还没有 `maxRounds` 字段的读取逻辑。

拟新增的使用方式：

```js
__NLJS_GLOBAL.maxRounds = 10;

async function sum(a, b) {
  return nl`返回 a + b`;
}
```

向既有对象赋属性，不重新声明或整体替换 `__NLJS_GLOBAL`，也不修改 Babel 的参数传递接口。这个对象在当前 Node/CommonJS 示例中属于当前编译文件，不是进程的 `globalThis`；配置不会自动影响其他文件。

配置契约：

- 未设置 `maxRounds` 时默认 10，首轮也计入上限。
- 配置值是大于零的安全整数；字符串、`null`、零、负数、小数及非有限数无效。
- 在 OpenAI 缓存未命中时读取；非法值在请求模型前报错。Jev 与缓存命中不读取这个生成配置。
- 每次新生成读取一次并固定为本次会话的上限，运行中的会话不跟随对象后续修改。
- SDK 自身的 HTTP 重试不作为新的会话轮次。

## 主循环与结束条件

1. `generate()` 沿用现有 provider 分流及代码缓存；只有 OpenAI 缓存未命中时进入 Harness。
2. 创建本次会话独立的初始 messages，固定模型、配置和上下文，从第 1 轮开始请求。
3. 收到有效的唯一 `final_output` 时，返回其 `asyncFuncBody`，立即结束生成阶段，无需再向模型请求总结。
4. 遇到可修正问题时，保留本轮 assistant 消息，按下表补充反馈，然后进入下一轮。
5. 如果本轮已达到上限，则直接抛出包含末次失败原因的生成错误，不再发起请求；不可修正的错误立即终止。

请求继续使用 Chat Completions，强制指定 `final_output`，设置 `parallel_tool_calls: false`，不增加 `strict: true`。工具 arguments 仍只能是包含字符串 `asyncFuncBody` 的 JSON 对象，不读取正文或 XML 补救。显式空函数体仍是有效提交。

## 响应与错误处理

| 情况 | 处理 |
| --- | --- |
| 正常结束、没有工具调用 | 保留 assistant 回复，追加 user 提醒，继续下一轮 |
| 完整工具调用的 arguments 不是合法 JSON，或 JSON 字段不符合约定 | 以 tool 消息反馈具体校验错误，允许下一轮重新提交 |
| 完整的 function 调用使用未知工具名 | 以 tool 消息说明仅有 `final_output` 可用，继续下一轮 |
| 同轮多个完整调用，各自 ID 可区分 | 本轮不采用任何一份提交；逐一反馈错误，请模型下一轮明确提交一份 |
| 拒绝、内容过滤、截断 | 立即失败 |
| 响应结构损坏，不能构造合法后续历史 | 立即失败 |
| 请求失败 | 沿用 SDK 自身处理，不增加 Harness 网络重试 |
| 已提交代码的 JavaScript 语法或执行错误 | 保留既有执行路径处理，不进入 Harness 修正循环 |

“同轮多个调用”是一次模型响应携带多个工具调用，不是多个轮次里反复修正提交。该轮多份函数体都不作为结果；不擅自选择第一份或最后一份。下一轮可以再次调用工具提交明确结果。

生成成功只表示提交协议校验通过，不保证函数体语法或行为正确。生成阶段失败不写缓存；有效提交仍按原路径包装并缓存，实际执行由调用处的 eval 完成。

## 消息续写的协议约束

已核对本地安装的 OpenAI SDK 类型：函数工具调用包含字符串 `id`、`type: "function"`，以及字符串 `function.name` 和 `function.arguments`。工具反馈为 `role: "tool"`，通过 `tool_call_id` 指向原调用，并以 `content` 反馈结果。

- 漏调用时，保留本轮 assistant 回复，再追加 user 消息，提醒通过 `final_output` 提交函数体。
- 调用参数校验失败时，保留原工具调用，通过对应的 tool 消息返回具体错误。即便 JSON 解析失败，原始 arguments 字符串仍可保留。
- 若一个响应包含多个调用，继续前需要逐一反馈，不能遗漏其中某个调用。
- 参数内容不正确与响应结构损坏需要分开：例如 arguments 是对象而不是字符串、工具调用缺少可关联的 ID，均不能直接当成普通参数错误续写。续写中的调用 ID 必须非空且互不重复；这是本项目的约束，不是本地 SDK 类型所能保证的服务端行为。
- 缺少 choice / message、错误的消息角色、不支持的工具类型，以及结束原因和实际工具调用不一致，归为损坏响应；不伪造工具 ID 或改写损坏字段来续写。

保留收到的 assistant 消息，避免在裁剪字段时丢失已有的服务附加内容；不自行生成推理字段。

## 拟定的模块职责

- `generate()` 保留 provider 分流、上下文构造、缓存检查、配置快照、函数体包装和成功后的缓存写入。
- 新的内部 Harness 模块维护本次调用专用的 messages、轮数、工具定义、响应分类、参数校验及错误反馈，成功返回 `asyncFuncBody`。
- 每个自然语言片段的每次生成拥有独立消息历史；并发生成不共用对话，已有的 scope 与源码上下文不在轮次之间重新采集。
- 不新增公共调用方法，不在 Harness 内执行生成代码；Babel / eval 与 Jev 保持现有职责。
- 生成提示词允许提交错误后再次修正，要求每轮只提交一份最终函数体，有效提交后结束会话。
- 耗尽轮数时抛出带有末次失败原因的生成错误，不再发起下一轮，也不缓存失败内容。

## 拟定的验证范围

- 首轮有效提交即结束，保留空函数体、正文不参与提取、函数体原文与现有执行行为。
- 漏调用后提醒，参数错误后按原工具 ID 回填错误，再提交成功。
- 多轮消息顺序与内容保留；未知工具可修正，同轮多个调用逐一反馈，损坏响应直接失败。
- 默认上限为 10；第 10 轮成功与第 10 轮仍失败分别验证，没有第 11 次模型调用。
- `__NLJS_GLOBAL.maxRounds` 覆盖默认值，非法配置不发请求；当前会话使用快照，不同调用彼此独立。
- 生成阶段失败不写缓存；修正成功后缓存仍复用；Jev 与缓存命中不受轮数配置影响。
- 并发生成的消息历史互不混入。保留 core 与 Babel 现有测试，使用模拟模型响应验证，不用真实模型结果代替控制流断言。

本方案涉及 core 的内部 Harness、生成提示词、测试和使用文档。实现时同步 README 与原工具协议设计中的单轮错误处理说明，完成情况由本地工单记录。
